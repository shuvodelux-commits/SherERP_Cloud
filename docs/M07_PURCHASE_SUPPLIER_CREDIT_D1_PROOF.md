## Source semantics

`refundMethod='Supplier Credit'` produces a linked new Purchase Return and removes the returned quantity from the **original purchase's lot** and shop stock. Its `SUPPLIER_LEDGER` Credit entry references the Return ID and stores **the original Supplier ID and signed post-credit Balance**. The original Supplier's signed `Current Due` decreases by the full return amount; zero can become negative, which represents **supplier advance/receivable**. There is **no Cash-refund paid ceiling** for Supplier Credit, so a fully unpaid original purchase may be returned for credit. There is **no new Cash/Bank movement**, no repayment and no change to any other account on the same Party. Original M05 supplier `payable_paisa` and original purchase receipt/paid amount stay unchanged in this synthetic proof.

M05's `m05_suppliers.payable_paisa` is a test-only non-authoritative older account projection. M07-B2 creates disposable **`m07_purchase_supplier_signed`** seeded *after* the real M05 purchase is committed; this is a signed oracle to prove the future M08 account boundary, **not** a second permitted production ledger. Only M02-P/M08 may choose the authoritative signed production supplier account and reconcile historical opening/current obligations. Never auto-net with Customer, Vendor, Owner, Lender, Borrower or Payee.

## SQL transaction and contract

`tests/fixtures/m07-purchase-supplier-credit-contract.mjs` exports test-only `createSyntheticD1PurchaseSupplierCreditContract(DB,{beforeBatch?}).post(input)`. Strict bounded IDs/actor/source with `{tenantId,actorId,purchaseId,supplierId,returnId,operationId,sku,lotId,originalHash,units,creditPaisa,reason}`, exact integer paisa and source hash, SHA256 M03 canonical operation fingerprint, `COMMITTED|REPLAY|CONFLICT|DECLINED`, and `NEEDS_REVIEW` if SQL completion is uncertain. No browser/user-controlled role or arbitrary SQL accepted.

`tests/fixtures/m07-purchase-supplier-credit-schema.mjs` adds only disposable local D1 `m07_purchase_supplier_signed`, `m07_purchase_credit_returns`, `m07_purchase_credit_ledger`, and triggers. SQL BEFORE INSERT validates current Cash Session, exact original immutable M05 purchase/item/lot/original stock movement, purchase Supplier ID, reviewed and matching Supplier→Party link, active signed account, original net (invoice discount-adjusted) item price, source lot availability and shop stock. It also refuses a Cash Purchase Return with the same Return ID or Operation ID. SQL AFTER INSERT updates the **same source-lot remaining record shared by Cash and Supplier Credit**, decreases the shop stock, writes the same outgoing stock movement and then subtracts Supplier signed due and appends one Supplier ledger row storing the **post-credit Balance**. If a later child fails, SQLite rolls back **all** prior lot/stock/money/receipt writes.

A separate SQL test-only BEFORE INSERT trigger on `m07_purchase_cash_returns` rejects IDs already used by Supplier Credit. The prior Cash adapter deliberately reports `DECLINED` for such a foreign-method receipt; Supplier Credit's unified receipt readback identifies existing Cash collision as `CONFLICT`. Distinct Cash and Supplier Credit returns may each consume legitimate remaining source units, but must not reuse Return ID/operation ID or exceed original purchased-minus-returned quantity.
