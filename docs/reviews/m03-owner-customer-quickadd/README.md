## Contract and single writer

- **Authoritative Shop D1 migration:** `staging-migrations/shop-owner-write/0015_owner_customer_master.sql`, applied after Party Identity and Owner Write Lease; **local-only** until a separate production migration and backup approval. This creates `owner_customer_create_receipts`, `owner_customer_master`, one linked `parties` record and `party_roles(Customer)` per create. It refuses previously imported Customer roles/legacy links. Existing Supplier identities remain separate (`PTY-CUS-000001` versus Supplier `PTY-000001`). It does not create or mutate any financial ledger, payment, due or credit account.
- **Private Owner routes** (no public RPC): `GET /api/owner/customers` → `{success:true,data:{customers:[source-shaped],bankAccounts:[],currencySymbol:''}}`; `POST /api/owner/customers` → `{success:true,data:{id:'CUS-000001'}}`. Requests require active signed Owner session, current Shop identity/binding and write-grant (SQL time); `OWNER_CLEAN_PRODUCTS_ENABLED=true`, `OWNER_WRITE_GRANTS_ENABLED=true`, **new `OWNER_CUSTOMERS_ENABLED=true`**. Default flag absent means **404 and no route activation**. Staff access is not granted by this Owner-only endpoint.
- **Strict input:** valid v4 `operationId`, Customer name/phone, optional father/husband relationship, address, notes and **exactly zero opening balance**. Names and phone are not unique. No auto-merge across source identities or Party roles. Canonical hash + immutable receipt distinguish replay from mismatched reuse of an operation ID; a D1 trigger makes the Party/role/Master creation one atomic transaction. Cancellation invokes no backend write.
- **Existing frontend API translation:** original `serverCall('addCustomerChecked', authToken, payload)` uses one saved operation ID across uncertain retries; `serverCall('getCustomersBootstrap')` reads the real Shop Customer directory. The original POS `[+]` opens that same modal and selects returned Customer ID after refreshing POS bootstrap, **without clearing cart**. The original Customer page's create and list also work. Customer *edit, payment, advance, due* actions remain explicitly unavailable; no fake ledger.
- **POS bootstrap:** when the private flag is enabled, `/api/owner/pos/bootstrap` projects real Customer `{id,name,phone,fatherName,relationType,address,currentDue:0}` entries. When disabled, it preserves the original empty list. The current Cash-only Sale writer still rejects registered-customer posting; selection does not bypass that gate.

## Security, accounting and rollback

- Wrong-Shop token/session denied; expiring the Shop write grant leaves zero Party/receipt writes; retry mismatch conflicts; same phone yields two independent records rather than merged balance; 1,000 records is a hard explicit read limit, not silent truncation. SQL-trigger failure proof asserts zero orphan records; original Cash Sale/Cash Return, FIFO and Cash Book unchanged.
- No changes to `legacy/source`, source manifests, cash/stock posting migrations, Store Credit, M07 Return SQL or M08 Customer advance ledger. No live D1/customer data changed by this branch. **Do not enable `OWNER_CUSTOMERS_ENABLED` before migration/backup/rehearsal and owner approval.** To roll back UI reachability, disable the flag; do not remove immutable Customer histories after they have been created.
- Next reviewed PR: typed guest paid/registered Cash attribution (`customerMode` and versioned receipt handling), followed separately by atomic Store Credit Return and Customer advance liability/ledger. Existing Customer **selection is not yet evidence that registered Sale posting works**. Split payment and mixed units remain independently gated.
