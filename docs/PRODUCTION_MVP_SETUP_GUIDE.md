# SherERP Cloud setup and release checks

**Release decision for the code inspected at 0deb878e: hold production.** You can connect GitHub and publish a demonstration shell in a new Cloudflare account. The private sign-in screens and database components have separate entry points. A new account still needs an installer for its first administrator, a hosted business provisioning flow and a connected financial ERP. Completing the shell setup does not give you a working shop.

Use this guide for a fresh account. Keep your existing ERP running and use made-up records for acceptance checks. Sections E through G describe the screens and results to check on an approved private candidate. Stop at the first unavailable step.

## Part A — Accounts and limits

1. In GitHub, open **shuvodelux-commits/SherERP_Cloud → Code** and select **main**. Confirm you see `wrangler.preview.jsonc` and `package-lock.json`. You need repository access and permission to install or approve the Cloudflare GitHub App for this repository. An organization owner can grant that access.
2. Sign in to the Cloudflare dashboard, select your intended account and open **Workers & Pages**. Use an account that can create a Worker and configure Builds. If prompted to choose a workers.dev subdomain, choose an available label for your account. Record it and the account ID privately. Check the account name before creating resources. D1 creation requires D1 write access in that account. Access application management is a separate permission for the future private administrator site.
3. For private rehearsal, use a Google account with permission to create a Google Cloud project or configure OAuth clients and branding in an existing one. Have a second Google identity for a test Shop Owner and a separate authenticator for the administrator. No SMS service is configured by these private sign-in screens.
4. You can start the shell on Workers Free without Workers for Platforms. The published free limits include 100,000 Worker requests per day, ten D1 databases per account, 500 MB per database, 5 GB total storage, five million D1 rows read and 100,000 rows written per day. Allow capacity for a control database, separate shop databases and disposable recovery tests. Measure usage during rehearsal before selecting a plan. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

## Part B — Connect the demonstration shell to GitHub

1. In Cloudflare, open **Workers & Pages → Create application → GitHub**. Choose your GitHub account. On the GitHub authorization screen, select **Only select repositories** and grant access to **SherERP_Cloud**. Back in Cloudflare, choose that repository. If it is missing, check the GitHub App installation for the organization that owns it. [Connect a Worker](https://developers.cloudflare.com/workers/ci-cd/builds/)
2. Use these dashboard field values. Paste commands into the indicated **Builds** fields. Cloudflare runs them for you. The project’s supplied operating instructions mention `shererp-cloud-preview`, while the versioned preview file and its guard both require `hisabiq`. In a fresh account the instructions below target the name verified in the file. If you already have either Worker, confirm which service you own before connecting or replacing it.

   | Field | Value |
   | --- | --- |
   | Worker / project name | `hisabiq` |
   | Production branch | `main` |
   | Root directory | Repository root (leave the default) |
   | Build command | `npm run build:frontend && node scripts/check-cloudflare-preview.mjs wrangler.preview.jsonc` |
   | Deploy command | `npx --yes wrangler@4.161.0 deploy --config wrangler.preview.jsonc` |
   | Preview command | `npx --yes wrangler@4.161.0 preview --ignore-base-config --config wrangler.preview.jsonc` |
   | Build variable if Node selection is needed | `NODE_VERSION` = `22` |

3. Review the build token's account and permissions. Workers Builds supports a generated user token or a selected token. Creating the Worker requires permission to create Workers in this account. For ongoing code deployments the existing Worker needs Editor access (or Workers Scripts Edit). The shell uploads Worker code and static assets and uses workers.dev. It has no use for D1 access, a Google secret, a global API key or shop credentials. Cloudflare's generated token can have broader rights. Review its scopes under **My Profile → API Tokens**. Keep credentials out of GitHub Actions and branch previews. [Worker permissions](https://developers.cloudflare.com/workers/authorization/workers/) · [Build settings and generated token scopes](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)
4. Choose **Save and Deploy** for the shell. Under the Worker’s **Settings → Builds**, verify the connected repository, branch and both commands. Enable builds for the non-production branches you want previewed. Under **Deployments**, compare the deployed commit with the approved GitHub commit. An approved merge to main should update the shell. A feature branch should get its own preview URL. Test both links in Part G. GitHub Actions validates changes. Cloudflare Workers Builds owns publishing. [Git integration](https://developers.cloudflare.com/workers/ci-cd/builds/git-integration/)

## Part C — Cloudflare resources

1. Open **Workers & Pages → hisabiq → Bindings**. Check that the Worker has its static assets and no D1 bindings. Under **Settings → Variables and Secrets**, keep the public shell free of private configuration. Do the same for branch previews. Open the URL shown by Cloudflare and append `/api/health`; expect `status: foundation` and `database: not-connected`.
2. **Private preparation only.** If you have approved a disposable account rehearsal, open **D1 SQL database → Create Database**. Enter a distinct database name, select the intended location, click **Create**, and record the displayed name and database ID. Repeat for a shop. Example names are `my-erp-control` and `my-erp-shop-one`. Leave these empty until the migration procedure for this account is approved. [Create a database and configure bindings](https://developers.cloudflare.com/d1/get-started/)
3. Compare the proposed private deployment with the following inventory. A binding is the name the server uses to open a specific database. Check both the name and the database ID. Never use the account IDs, database IDs or rate-limit namespaces in checked-in staging and test configurations as values for a new installation.

   | Worker role | Entry point and resources | Required runtime configuration |
   | --- | --- | --- |
   | Private administrator | `src/m03-access-platform-auth-worker.js`, `CONTROL_DB` pointing to the control database, `PLATFORM_INGRESS` rate limiter | `PLATFORM_AUTH_SCOPE=private-platform-auth`, `PLATFORM_AUTH_ORIGIN` = exact admin HTTPS origin, `PLATFORM_CLIENT_ID` from Part D, `PLATFORM_ACCESS_AUDIENCE` from the Access application, `PLATFORM_ACCESS_EMAIL` = approved lower-case operator email, `PLATFORM_TOTP_SECRET` and `PLATFORM_FACTOR_VERSION` paired to the enrolled factor |
   | Private pilot Shop Owner | `src/m03-owner-redemption-worker.js`, assets built by `npm run build:owner-frontend`, `CONTROL_DB`, `PLATFORM_PILOT_DB` pointing only to its shop, `OWNER_INGRESS` rate limiter | `OWNER_AUTH_ORIGIN`, distinct `PLATFORM_AUTH_ORIGIN`, `PLATFORM_OWNER_CLIENT_ID`, `PLATFORM_PILOT_SHOP_ID`, `PLATFORM_PILOT_D1_ID` and `PLATFORM_PILOT_MARKER` matching the provisioned shop |

4. In an approved private release, inspect **Worker → Bindings** and **Settings → Variables and Secrets**. Use **Secret** for the administrator's authenticator seed. The private enrollment process must securely supply the seed, matching factor version and ticket. Store recovery information privately. After activating Zero Trust on your account, open **Workers & Pages → private administrator Worker → Access** and protect **All traffic**. Select an Allow policy for the designated operator email. Copy the application audience from the Access application into the administrator Worker’s audience field. Check that a signed-out browser and a different identity cannot reach the administrator page. The current private profile generator leaves both hosts disabled. [Protect one Worker](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)
5. **Stop before private publication or migration.** The portable profile generator in `scripts/port-p1-instance.mjs` produces disabled drafts. The private Worker names must differ from each other and from the reserved public name `hisabiq`. The hosted preflight checks existing databases and each rate limiter’s binding name, namespace, limit of 20 and period of 60 seconds against the expected settings. Release engineering can run `npm run rehearse:private-bundles` in a disposable checkout dedicated to synthetic tests to generate both profiles for a synthetic account and bundle both Workers in dry-run mode. A green bundle check confirms the code can be packaged. Live Access, Google login, migration and deployment checks still require the target account. The shop's six-file ordered migration list in `src/db/m03-owner-ready-shop-migrations.js` covers identity and catalog. The manual GitHub workflow targets one pre-existing staging account and stops its apply step when the migration count differs from two. It cannot initialize a fresh production account. A release must select the correct control and shop migrations, verify backups, apply them once, verify receipts and resume interrupted setup before operating these databases.

## Part D — Google sign-in

1. In Google Cloud Console, use the top project selector to choose the intended project or **New project**. Open **Google Auth Platform → Branding**. Enter the display name users should see, a monitored support email and the required developer contact. Supply links on domains you control where Google requires them. Save and check the project name at the top. [Google sign-in setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)
2. Open **Audience**. For a rehearsal involving consumer Gmail accounts, choose **External**, keep the app in testing and add only the approved test accounts under **Test users** if that option is present. Check that the addresses match the accounts you will use.
3. Once you have the approved private Worker origins, open **Clients → Create client → Web application**. Enter a recognizable name. Under **Authorized JavaScript origins**, add the exact HTTPS origin for each private host from Part C. An origin contains the scheme and hostname only. Get the addresses from the intended account, without a route, wildcard or query string. Leave **Authorized redirect URIs** empty for these screens. Both use the Google Identity Services popup and pass an ID token to their own server. The app defines no redirect callback path for this flow. Save and copy the **Client ID** to the two client-ID fields in Part C. These Workers do not consume an OAuth client secret. [Create a web client and register origins](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)
4. On the approved private candidate, choose **Start sign-in**. Verify that Google shows your app name and the intended Google account. An origin error calls for checking scheme, hostname, client ID and project against the Google client. A 403 before the Google screen calls for checking the administrator Access policy, audience and email. A 404 on the Owner screen can mean that the route is disabled. A 503 can mean that required bindings or configuration are missing. Preserve the UTC time and sanitized error text when reporting a problem.

## Part E — First Super Admin

1. **Blocked on a fresh hosted account.** The server requires a single-use, preapproved setup ticket tied to the Google identity and a configured authentication factor. There is no verified dashboard issuer for the initial ticket and factor. Request the private installer and recovery test from the release maintainer. A database edit, a sample ticket or enabling a flag cannot substitute for enrollment.
2. When a reviewed installer supplies the private administrator URL, setup ticket and paired authenticator, complete Cloudflare Access, select **Set up administrator**, enter the **Setup ticket**, choose **Continue setup** and select the enrolled Google identity. Keep the ticket out of chat and build logs.
3. Select **Start sign-in**, choose that account and enter the current authenticator code. Expect **Signed in as Platform Super Admin**. Sign out and confirm a new browser session requires authentication. Test that the Shop Owner account cannot open the Control Center.

## Part F — First business and Shop Owner

1. **Blocked on hosted provisioning.** In the disposable local candidate the administrator can enter **Business name**, enter the intended **Owner Gmail** when displayed, and click **Create business**. Open **Recent businesses (up to 50)** to inspect the result. Use **Resume setup** for a pending operation. A ready directory entry alone does not establish that the ERP can post a sale.
2. Before inviting an Owner on a hosted candidate, the installer must verify the shop/database identity, migration receipts and account-specific bindings. A second independently provisioned shop is required to check isolation. The candidate Owner Worker binds a single pilot shop. There is no verified dashboard flow for adding a new hosted shop, suspending and reactivating it, or authorizing support access.
3. In invitation mode on a reviewed candidate, open the private Owner URL, select **Accept invitation**, enter the private **Owner invitation code**, choose **Continue setup** and use the invited Google identity. In approved-Gmail mode choose **Start sign-in** and use the Gmail selected for that shop. Confirm the business name and sign out. Sign in again and check that the same business opens.
4. **First sale remains blocked.** The Owner Worker exposes scoped catalog routes and the original shell. A hosted end-to-end settings, purchase, POS, correction and accounting flow is missing. Do not enter actual opening balances or issue customer invoices. Use the tests in Part G once the shop’s financial routes are connected.

## Part G — Verify a candidate

1. For the shell, open **Worker → Deployments**, choose the displayed main URL and a branch preview URL, and open `/api/health` on both. Expect JSON including `service: shererp-cloud`. Open the base URL on a desktop and phone. If the health URL returns HTML, check the configuration filename and the `/api/*` Worker route. If the build fails, open the failed **Build** log and check Node version, lockfile installation and the frontend build step.
2. For a private candidate, complete Parts D through F twice using distinct disposable businesses and accounts. Reopen each account in a separate browser profile. Shop A’s products, invoices and balances must be absent in Shop B. Have the release tester verify that the server also rejects attempts to read or change Shop A records using Shop B’s session. Verify logout and revoked access on a previously open tab.
3. Enter a synthetic supplier, customer, shop settings and product. Example, with no tax or discounts: receive 10 pieces at 5 each on supplier credit, then sell two pieces for 8 each in cash with an active cash session. Check stock of 8 pieces, supplier due of 50, cash increase of 16 and cost of goods sold of 10. Refresh and sign back in. Verify those numbers again and print the invoice. Repeat the same submission with the same operation ID in the automated rehearsal; expect one posting.
4. Return one sold piece and refund 8. Confirm stock of 9, net sale of 8 and net cost of 5. Record a cash expense of 2 and a supplier payment of 5. Expect a net cash increase of 1 from the opening amount and a remaining supplier due of 45. Separately test customer credit and collections, a bank payment, purchase return, a multi-supplier FIFO sale and a box/piece/square-foot invoice against the product's actual conversion. Compare invoice lines, stock, independent ledgers and reports. Record a failed or missing flow by name.
5. Confirm that the approved GitHub commit, private deployment, database IDs, authentication checks, two-shop denial tests, financial totals, backup restore and Worker rollback all match the release record. Any missing evidence keeps the production decision on hold.

## Part H — Daily operation and recovery

1. For updates, review **GitHub → Pull requests → Checks**, approve the exact commit and merge only after approval. In Cloudflare verify the deployed commit and repeat the health check. Automatic deployment today covers the shell. Keep the existing ERP as the system of record.
2. To add a business or change an Owner, use the reviewed private administrator flow only once available. Until hosted provisioning and revocation pass Part G, record the intended business, owner and needed change privately. Never share a pilot database binding between independent businesses to get around this limit.
3. Before a private update, record the UTC cutover time, Worker version and recovery point for the control database and every affected shop. D1 Time Travel is automatic and retains seven days on Free or 30 days on Paid. For longer retention use a protected export and verify it by restoring into a disposable database. A single database restore cannot establish agreement across shops and the control database. A tested coordinated restore and reconciliation procedure is still required. [D1 recovery](https://developers.cloudflare.com/d1/reference/time-travel/) · [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
4. For a bad shell release, open **Workers & Pages → hisabiq → Deployments**. Locate the previous verified version, select its **… → Rollback**, and verify its URL and health. Fix or revert the offending change through GitHub before the next merge. A Worker rollback changes code and assets. If data has changed, pause writes and obtain owner approval for a separate database recovery. [Worker rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
5. Review **Workers & Pages → your Worker → Metrics** and each **D1 SQL database → your database** for usage. On repeated quota errors, preserve error times, examine daily row reads/writes and request counts, and check the current plan before adding another shop. Never rerun a financial submission with a new operation ID just because a response timed out.

**Ready for real records only when the private hosted rehearsal succeeds.** The owner can connect the shell and prepare account access today. Engineering still owns the private installer, secure bootstrap, shop lifecycle, financial routes and coordinated recovery rehearsal.
