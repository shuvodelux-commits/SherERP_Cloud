# ADR M02-001 — Initial D1 catalog tables (review required)

**Status:** Proposed; implementation branch only.  
**Original source:** `Mohim_ERP` commit `29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`.  
**Source mapping:** `docs/baseline/schema-inventory.json` (49 groups / 659 columns).

## Decision

Use an explicitly typed SQLite **STRICT** migration `migrations/0001_core_catalog.sql` for only these three low-risk groups, before any financial, stock or user-authentication tables:

| Sheet | SQL table | Legacy columns mapped |
| --- | --- | --- |
| SETTINGS | settings | Key → key, Value → value |
| PRODUCT_CATEGORIES | product_categories | Category ID → category_id, Category Name → category_name, Status → status, Created At → created_at |
| PRODUCT_UNITS | product_units | Unit ID → unit_id, Unit Name → unit_name, Status → status, Created At → created_at |

Each table receives `row_id INTEGER PRIMARY KEY AUTOINCREMENT` as a stable internal surrogate and nullable, individually unique `legacy_sheet_row INTEGER` for import traceability. Legacy IDs / setting keys retain explicit uniqueness. We do **not** base application identity on implicit SQLite row order.

**Critical compatibility choice:** Neither category nor unit name has a unique SQL constraint or a foreign key from PRODUCTS. The source `ProductSettings.gs` permanently deletes category/unit label rows and permits creating another row with the same name. Products store the plain category/unit *label*, not a foreign key. A hard DB uniqueness or cascading FK would change original behavior. A comment in Config.gs describes a different intended policy; the executable source behavior and tests take precedence pending owner review.

Settings and master-data IDs, labels, statuses and created-at values use TEXT to preserve original textual forms. Legacy numeric/boolean **settings values** normalize to strings; their semantic interpretation belongs in the compatible settings helper, not unreviewed SQLite numeric coercion. Phone identifiers retain leading zeros. Historic timestamps are not silently reinterpreted as UTC; date policy is a separate ADR. Created At remains TEXT without an ISO CHECK until the source export formats have been reviewed.

## Validations

- Unique stable legacy identifiers; reject blank keys and names; duplicate source IDs and legacy row offsets are rejected **before** planned writes.
- No uniqueness constraint on category/unit label, because the original business code allows reuse after deletion.
- SQLite migration tests execute real SQL against in-memory SQLite 3.37+ (Node 22 `node:sqlite`), including error behavior for duplicates and constraints.
- Offline `prepareCatalogImport` validates *only* these three source sheet groups and returns normalized rows plus a PII-free summary. CLI `npm run catalog:dry-run -- tests/fixtures/catalog-synthetic.json` never writes a database.
- CI verifies this typed map against the full **frozen** source inventory, not only small synthetic tests.

## Excluded / deferred

- No full 49-group SQL migration yet; no schema for product quantities, FIFO lots, sales, returns, cash, bank, ledgers, users or tokens.
- No production D1 binding, migrations apply, Cloudflare deployment, live Sheets export, data import, database writer or credentials. The importer is an **offline dry-run only**.
- Financial DECIMAL/money precision, quantity-unit conversions, exactly-once posting, cash-session policies, and historical audit/deletion preservation require separate migrations and tests before production use.
- No promise that live source data is clean; the eventual importer must reconcile duplicates and malformed Sheets rows explicitly, never silently discard them.

## Tooling / commands

```bash
npm test
npm run inventory:schema
npm run catalog:dry-run -- tests/fixtures/catalog-synthetic.json
```

Cloudflare supports versioned numbered `.sql` migrations applied with `wrangler d1 migrations apply <DB_NAME> --local`; **do not run `--remote`** against production before owner-approved backup/rehearsal. Official D1 docs: https://developers.cloudflare.com/d1/reference/migrations/ and https://developers.cloudflare.com/d1/worker-api/.

## Review gate

Merge only if migration SQL, source-map, tests, and dry-run are green. This marks the **three-table schema slice** complete—not all of M02, nor a functional ERP backend.
