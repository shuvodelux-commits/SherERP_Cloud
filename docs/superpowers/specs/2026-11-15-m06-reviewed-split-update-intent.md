## Rationale
The merged M06 read model and split Update preview are separately correct, but they cannot be treated as permission to post. Before an eventual D1 writer can review an edit, the source requires historical original Cash Session still Open, no active return, unique un-deleted invoice, valid previous split tender, reconcilable original Cash/Bank book evidence, and unchanged later Customer settlement. This composition prevents a financial proposal accidentally bypassing one of those gates, without creating a competing ledger engine.

## Contract
New internal pure function `planReviewedSplitSaleUpdate(snapshot,{canEditSales})`.

Trusted tenant-scoped `snapshot` must contain `invoiceId, sales, items, paymentRows, returnItems, sessions, bundleComponents, vendorSourcing, cashBookRows, bankBookRows, currentSettlement, newItems, discount, newPayments, bankAccounts`. All records are plain data with own value properties only; all row collections must be complete, already authorized and tenant-scoped. `currentSettlement` represents the **reconciled current state** from M08, never the requested payment change. `canEditSales` MUST come from M04 server authentication and must never be exposed as a user-supplied request flag.

Call already-proven `projectSaleForUpdate(invoiceId,snapshot,{canEditSales})` first to ensure unique source header, non-deleted status, original source snapshot/payment integrity, active returns absent, historical Cash Session Open, and Bundle snapshot consistency. Then require historical Payment Detail Version exactly `1`. Compare current settlement paid and due to the original checkout `Paid Amount` and `Due Amount` using original integer-paisa semantics. Any later Customer collection, credit, return adjustment or mismatch is **Needs Review** rather than an apparently safe edit. Validate all original checkout Cash/Bank postings against original `readSalePaymentBreakdown_` via `assertSalePaymentBookEvidence_`; a mismatch fails closed. Confirm the next SALE_PAYMENTS revision is a positive safe integer, with original active payment IDs retained as read-only evidence. Only then call merged `planSplitSaleUpdatePreview` with the same exact source invoice, historical sale/rows, requested candidate lines and replacement payments. Calculate signed account deltas from the original source checkout applied amounts to the proposed applied payments via existing `salePaymentAccountDeltas_`.

Return `{original,preview,nextRevision,reversedPaymentIds,accountDeltas}`. The original Customer ID is retained only in the original source projection, never inferred from phone/name or Party roles. `reversedPaymentIds` and deltas are *preview evidence*, not instructions to write directly. Cash change/tender is not Cash Book income. A version-1 invoice that was entirely Due may legitimately have zero active SALE_PAYMENTS; next revision begins at 1. Multiple Bank/Mobile payments and Cash change follow the already source-proven allocator.

## Explicit exclusions and ownership
No D1, SQL, migrations, caller auth, API route, source GAS or original frontend changes. No atomic posting, Cash/Bank/Customer ledger mutation, stock FIFO changes, return cancellation or financial settlement. The M03 shared SQL transaction writer MUST re-fetch and recheck all predicates, operationId, payment revisions, immutable journal and affected stock/ledger rows under DB-enforced CAS/atomicity. The M04 actor, M05 FIFO, M07 returns and M08 reconciled Customer/finance relationships still own their boundaries. This is preparatory, not transaction-module production readiness.
