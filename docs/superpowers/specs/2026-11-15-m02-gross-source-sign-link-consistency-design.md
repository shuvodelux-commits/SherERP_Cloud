# M02-P — Gross Checkpoint Single-Source Party/Sign Consistency

**Date:** 2026-11-15. **Frozen original:** Mohim_ERP@29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2. **Authority:** AGENTS.md, docs/WORKSTREAMS.md, docs/M03_PARALLEL_READINESS.md and ADR-007 Unified Party. **Dependencies:** merged #202 (offline exact-checkpoint comparator), #213 (synthetic local D1 parity), #264 (source/field/account/basis tuple guard).

## Problem
The merged `reconcileGrossPartyCheckpoints` rejects impossible source/account tuples, duplicate identical expected checkpoints and wrong BDT minor-unit totals, but it still does **not** test internal consistency among *different expected checkpoints*. A source preflight could simultaneously carry both `CUSTOMER_RECEIVABLE` and `CUSTOMER_ADVANCE` for the same Customer ID, basis and signed `Current Due` cell, or an `OWNER_EQUITY` and `OWNER_ADVANCE` pair for one Finance Person ID's derived owner position. If the caller recomputes kind totals and provides identical readback, the existing comparator currently claims `offlineCheckpointParity:true`. Also, the same `CUSTOMERS / CUS-001` source may point to Party A for current due and Party B for historical opening, or one Vendor's payable and receivable could point to different Party identities. A correct single-source plan must never do that. These are internal preflight contradictions, not permitted settlements or changes in legal ownership.

## Decision
Within the existing pure `src/party/gross-checkpoint-parity.js`, validate **expected source-side current+historical checkpoints together**, after strict original tuple validation but before examining readback:
1. Every exact `(sourceGroup,sourceId)` must map to **one** `partyId` across all current and historical checkpoints. Distinct source IDs, including records from the same original sheet and persons linked via explicit human-reviewed groups, may map to different or the same Party. Never join by name or phone.
2. Each **signed channel** `(sourceGroup,sourceId,basis,accountChannel)` can have **one economic direction** per original source snapshot. Mutually exclusive pairs are Customer receivable/advance, Supplier payable/advance, Owner equity/advance, Lender loan payable/credit, Borrower receivable/credit. Finance Person Owner, Lender and Borrower are **separate channels**, so one Finance Person can hold all three simultaneously, with independent directions. Vendor `Current Due` and `Current Receivable` are **two independent fields/obligations** and can coexist, never be silently netted. A current and historical opening from the same Customer/Supplier may point in opposite directions because these are different bases.
3. A conflicting *expected preflight* must fail closed using the **existing** generic `Gross checkpoint parity unavailable` error; never read caller-supplied readback or return IDs/amounts. Exact duplicate checkpoint behavior remains the existing `PLAN_DUPLICATE_CHECKPOINT` fixed-code report, not a new exception. Existing readback-only source/Party/sign changes remain fixed-code `MISSING_CHECKPOINT`/`EXTRA_CHECKPOINT` mismatch reports.
4. No new amounts computed for accounting; this is only a consistency check on already-derived private checkpoints. The verified genuine `prepareGrossPartyBalances` source preflight should satisfy the guard without modification. Offline validity is **not** signed reviewer authority, D1 financial-account reconciliation, source authenticity, permission to import, cash/bank posting or cross-role settlement.
