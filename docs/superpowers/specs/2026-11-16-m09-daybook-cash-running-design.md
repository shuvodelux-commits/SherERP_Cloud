## User intent and alternatives

The Day Book screen displays chronological transactions alongside the actual cash drawer running balance. A sum of Sales cash payments is not that balance: deposits, corrections and cash movements can differ. One approach is to put Cash Book SQL joins into the new Day Book RPC, but M03 owns the transport and M02/M05/M07/M08 business-ledger schemas remain under independent review. Another is to infer balances from visible Day Book cashIn/cashOut values; that would omit hidden corrections and the source Cash Book's actual movement history. **Chosen:** source-faithful, pure, internal chronological projection over *complete* normalized original Day Book rows and *complete* authoritative Cash Book entries provided by a future reviewed D1 adapter.

## Contract
`projectDayBookRunningCash(rows, cashBookRows)` accepts two required arrays of **already authorized, fully populated** source-shaped Day Book and Cash Book rows. Return a **new array** of Day Book rows, ascending by `ts` with `runningCashBalance` added (initially `null` before first actual Cash Book movement), and fill missing `time` from the ISO-like timestamp after `T` (without parsing timezone). Do not mutate or sort input arrays/records; preserve other fields for later `projectDayBookWindow`.

Replicate the frozen source chronology exactly: sort all document rows by lexical `ts`; index the last live cash-bearing source row by nonempty `referenceNo`, `ts` and its sorted index. For each actual Cash Book movement, identify its `Reference` and use `Created At` if present; when its Created At is within 30 seconds of the owning document, associate it to that document's timestamp and index. For old Cash Book rows missing Created At, if `Date` is `YYYY-MM-DD` or midnight `YYYY-MM-DDT00:00:00` and the owning document exists, use the document timestamp instead of treating midnight as a posting time. Corrections outside the 30-second window retain actual posting time. Tie-break equal timestamp Cash Book movements by `sourceIndex`, with unassociated entries at -1. Apply actual signed `Credit - Debit` deltas before or at the owning row's position; round **after each movement** with the original money helper, never simply recompute from on-screen cashIn/cashOut.

## Safety and parity
Require complete rows, no accessor/getter or inherited/colliding reference key, finite money values and canonical known timestamp/date formats. Reject missing Cash Book snapshots instead of silently reporting balances from an empty substitute. Truly empty arrays are permitted and return null balance. Validate Cash Book dates in the already-normalized business zone rather than convert midnight UTC or guess the shop timezone; do not use ambient current time. Owner document references and `Created At` are trusted only after source ID normalization; this function never authenticates a user, never queries D1, posts cash, changes accounts, silently nets Party roles or exposes a public RPC. Do not invent Cash Session openings or corrections.
