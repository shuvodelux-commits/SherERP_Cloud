# M06 — Sale Update Mode must refuse unknown saved payment-detail versions

## Design decision (owner M06 continuation)
The original migration source is pinned at `Mohim_ERP@29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`, especially `SalesManagement.gs::getSaleForUpdate` and `SalePayments.gs::readSalePaymentBreakdown_`. The preserved POS Update Mode is allowed only for an authorized `sales.edit` actor, an unreturned original invoice, and its matching open historical Cash Session. The existing pure `projectSaleForUpdate` already refuses duplicate invoice IDs, ambiguous vendor rows, and corrupted version-1 payment children. It handles `Payment Detail Version='1'` by returning the checked split-payment breakdown, while a blank version represents a genuine legacy single-tender invoice with no split children. However, an unfamiliar nonblank saved value such as `2` currently skips the payment breakdown and returns an empty `payments` array, even when historical paid amount and payment children exist. This might make Cash/Bank/Mobile details disappear from the Update Mode prefill and invite accidental financial correction based on incomplete history. Such a version is not a supported source transaction format, so accepting it would be unsafe. The reviewed remedy is to raise a deterministic `NEEDS_REVIEW` error before the edit prefill is returned, rather than invent a legacy payment or silently drop children. A blank legacy version, whitespace-only blank, and version `1` must continue to match the pinned source output exactly. No original GAS source data, journal, Payment rows, Cash/Bank book, stock quantity, Party account, permission or UI may be changed by the guard. The rule belongs in the pure read projection; the future D1 posting/editing kernel still must re-authorize and enforce all financial invariants atomically. This PR is a defensive historical-data integrity check, not approval to launch the production editing API.

## Acceptance
- **RED first:** a source-shaped sale with `Payment Detail Version='2'` must reject instead of returning empty `payments`; any other nonempty unsupported version must reject too.
- **GREEN:** require either blank legacy or exact `1` after existing normalization. Reject unknown nonempty values with `NEEDS_REVIEW: unsupported historical sale payment detail version in Update Mode`. Keep valid source parity, account identity, tender/change, session, return and bundle checks intact.
- **Scope:** `src/modules/sale-update-read-model.js` + `tests/m06-sale-update-read-model.test.mjs` and spec/plan docs only. No D1 schema/RPC, no live data, no Cash/Bank/Party posting.
- **Evidence:** source bug reproduction, real GitHub RED regression, exact-head full CI GREEN including Foundation/Node, local Workerd/D1, Chromium and Cloudflare safety. Leave draft PR unmerged until all checks pass and owner reviews.
