# M02-P — Offline Gross Party Checkpoint Parity (2026-11-15)

**Authority:** `AGENTS.md`, `docs/WORKSTREAMS.md`, `docs/M03_PARALLEL_READINESS.md`, owner-approved ADR-007, and the pinned original `Mohim_ERP@29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`.

## Problem

Merged #190 validates supplied original Party + Finance exports and gates the source-only `prepareGrossPartyBalances` account checkpoint preflight. The source preflight contains original Party IDs, source group/ID, distinct gross account kinds, current versus historical opening basis and integer BDT minor-unit amounts. There is no independently checked checkpoint parity interface to compare that **private source-side preflight** to a separately provided accounting snapshot. Comparing only total net Party balance would incorrectly pass equal-and-opposite Customer/Supplier obligations, two-way Vendor debt, Owner drawings, or separate Lender/Borrower relationships. The M02 Party money D1 tables **do not yet exist**, and their schema/cutover are not authorized, so no D1 calls or speculative SQL belong in this PR.

## Decision: pure redacted comparator

Add `reconcileGrossPartyCheckpoints({preflight,readback})` in a new `src/party/gross-checkpoint-parity.js`. **Both inputs are explicitly supplied private in-memory objects**. This is an offline contract and regression harness; the caller is responsible for obtaining trustworthy readback in a later approved migration. Neither the call nor a true result proves any actual D1 database state.

- `preflight` is the exact existing result shape from `prepareGrossPartyBalances`: `formatVersion:1`, pinned `sourceCommit`, `currency:'BDT'`, `readyForAccountDesignReview`, `blockingIssues`, `currentCheckpoints`, `openingCheckpoints`, separate `grossCurrentTotalsMinor` and `grossOpeningTotalsMinor`, and original `summary` counts and no-money-effects claim. Never accept a `readyForAccountDesignReview:false` plan; do not compare its readback, return `readbackChecked:false` and null parity flags. Invalid plan count, mismatched gross kind totals, nonzero cash/bank/posted effects or incorrect source pin likewise block readback with fixed `PLAN_*` issue codes. Invalid malformed outer structures throw fixed `Gross checkpoint parity unavailable`.
- `readback` explicitly contains `{currentCheckpoints:[...],openingCheckpoints:[...]}`, with each row having exactly these private checkpoint keys: `partyId`, `sourceGroup`, `sourceId`, `kind`, `amountMinor`, `basis`, `sourceField`. Rows must have nonblank literal string IDs and allowed source groups, known original gross kind, correct basis (`SOURCE_CURRENT` versus `HISTORICAL_OPENING`) and a strictly positive safe integer `amountMinor`. No partial missing data, coerced IDs, numeric IDs, negative/zero/noninteger money, duplicate key or silent fallback.
- Compare every row on **all** `partyId/sourceGroup/sourceId/kind/basis/sourceField` identity dimensions, then exact integer `amountMinor`. Never collapse by Party or net two gross account kinds. Exact account/source amount mismatch emits `AMOUNT_MISMATCH`; absent/extra/duplicate checkpoint emits respective fixed codes. Historical opening checkpoints must never become source-current cash or balances. Row order does not matter; duplication does. Reject extra structural fields to prevent accepting an unreviewed contract. Original deleted Finance events have no expected checkpoints when original preflight properly excludes them.
- Return exactly `{formatVersion:1,sourcePlanValid,readbackChecked,currentMatch,openingMatch,offlineCheckpointParity,counts:{expectedCurrent,observedCurrent,expectedOpening,observedOpening},issues:[{stage,code,count}]}`. Skip sets `readbackChecked:false`, parity flags `null`, observed counts `null`. Codes and stages are fixed vocabulary only (`PLAN`, `SOURCE_CURRENT`, `HISTORICAL_OPENING`); aggregated deterministic counts, never IDs, names, source group, exact account kinds, phone, reviewer reference or money. No raw exception text.
- `offlineCheckpointParity` is **not** bank/cash/session, D1, authenticated review, journal reconciliation, verified data-provenance or production import readiness. The original separate-account and human-approval invariants remain. No auto-identity merge, cross-role offset or settlement.
