# M09 — Day Book Bank Book source-reference deduplication and reversals

**Date:** 2026-11-16  
**Pinned source:** `Mohim_ERP@29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`; `legacy/source/DayBook.gs::ownedReferences_`, `getDayBookTransactions` “Standalone bank activity” block, `DAY_BOOK_OPEN_MAP`, `DAY_BOOK_DELETE_MAP`, `dayBookRow_`. Original UI in `legacy/source/daybook.html` is retained.

## Problem and current dependency boundary
PR #329 landed source-parity final Day Book filters/totals but expects deduplicated rows before filtering. PR #323 landed internal authorized Day Book bootstrap; M03 concurrently owns a *separate* internal bootstrap RPC wrapper (PR #335), not this financial feed. The source specifically records bank-paid invoices in both business document and Bank Book; blindly concatenating both would double count money. Source also distinguishes manually reversed Bank Book entries (a linked reversal row exists) from delete-voided entries (reversed with no mirror); dropping both loses compensating activity.

## Approaches
1. Build a new multi-table SQL ledger / full live Day Book: rejected; it would touch active M05/M07/M08 shared schemas and posting kernel and risk double counting before migration approval.
2. Reuse Bank Ledger per-account balance as a substitute: rejected; that is a different report and does not preserve document IDs, source ownership and transaction reversals.
3. **Chosen:** one small, pure, internal M09 projector over a trusted, complete, already-authenticated, already-source-filtered snapshot. Return just the `Bank` rows of the original `getDayBookTransactions`, source-shaped for subsequent M09 feed assembly. No D1 connection, posting, RPC, cache or UI changes.

## Interface and source contracts
`projectDayBookBankRows(snapshot, isAdmin=false, includeDeleted=false)` returns a **new array of the original `dayBookRow_` Bank-row objects** (no final `runningCashBalance` until the separate Cash Book movement pass). Snapshot is an own-data plain object with exactly these nine complete arrays: `sales`, `purchases`, `expenses`, `customerPayments`, `customerAdvanceRefunds`, `supplierPayments`, `financeTransactions`, `bankTransfers`, `bankEntries`. These are **already authorized and selected** original source-equivalent arrays; owner document arrays have the upstream soft-deletion filtering applied. Incomplete input MUST reject, never silently omit a financial source. Dates MUST already be canonical business `YYYY-MM-DD` strings supplied by a trusted upstream adapter (no `new Date()` timezone conversion or user-supplied timezone).

The source ownership set is `Invoice ID` (sales); `Purchase ID` (purchases); `Expense ID` (expenses); `Ledger ID` and nonempty `Customer ID` (customer payments + advance refunds); `Ledger ID` and nonempty `Supplier ID` (supplier payments); `Finance ID` (finance); `Transfer ID` (bank transfers). Any Bank Book row with nonempty `Reference` matching a listed owner's ID is **omitted**, leaving its original document to represent the movement once. Standalone deposits, withdrawals, charges, interest, bounced cheques and unmatched references remain. Blank `Reference` never self-collides; bank transfer activity is separately shown by its own source document, not duplicated.

For `Status === 'Reversed'`: a bank entry whose `Entry ID` appears in ANY Bank Book row's `Reversal Of` is a **manual mirrored reversal**, still displayed with original debit/credit (the mirror offsets it). Otherwise it is **delete-voided**, hidden by default and displayed as a Deleted, **zero-amount** Bank row only if the actor is an authenticated Administrator and `includeDeleted===true`. Both `isAdmin` and `includeDeleted` are explicitly supplied by a *trusted server caller* as strict booleans; this component is **not** an authorization gate and must not receive raw client actor input. The source outputs `sourceModule:'Bank'`, `sourceId:Entry ID`, `openPage:'bank'`, `deleteModule:'bank'`, exact `Bank` money directions (Credit=In, Debit=Out), `isDeleted`, `status` and source metadata.

## Validation and verification
Reject missing owner arrays, request getters/inherited keys, invalid record/accessor/scalar, malformed or non-finite Bank Book Credit/Debit, invalid business dates, unsafe actor flags, unexpected source-colliding proto keys. Do not silently recompute a true financial balance, cross-role netting or bank current account balance from these rows. A regression suite executes the **frozen source code itself** in Node VM as the oracle, using the original `ownedReferences_`, `dayBookRow_` and standalone-bank loop, to compare full output shapes, orders, fields and amounts for normal source records. Include synthetic fixtures for all owner types, reversed with/without mirror, admin deletion, blank/unmatched refs, mobile/bank account metadata, exact Bank source navigation and no input mutation. No real-D1 accounting parity is claimed for this pure module: local M04/Workerd bank/auth workflows still run as affected regression checks, but D1 transaction adapter and Cash Book reconciliation remain separate.
