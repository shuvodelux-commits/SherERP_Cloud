# M08 — Historical Bank Transfer header/two-leg audit on isolated local D1

**Workstream:** M08 #66, coordinator #456. **Base main:** `59b0e2e4b7184acf2f3645aca32da1cb1c6d5cb3`; predecessor #509 merged at `56065487cc5ca35c67178dbdcc33e722ee1bc298`. **Original pinned source:** `Mohim_ERP@29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`, `legacy/source/BankBook.gs:transferBetweenBankAccounts`, `legacy/source/BankLedger.gs:reverseBankEntry`.

## 12-sentence implementation overview

The original bank transfer creates a BANK_TRANSFERS header and two BANK_BOOK legs with the same Transfer ID. The outbound leg debits the source bank account, and the inbound leg credits the destination bank account. A transfer does not itself write the Cash Book. Existing M08 tests verify the original GAS emission, but not whether a migrated D1 snapshot still contains both exact legs. This slice provides a read-only audit of that historical transfer provenance in a disposable local Workerd/D1 database. It adds a dedicated STRICT test-only transfer header table and reuses M08's already isolated bank account/book test tables. Every read is tenant-bound and sorted by physical legacy row, not SQL insertion order or a guessed timestamp. Valid transfers must have one outbound and one inbound leg with exact account, reference, amount and active status. Missing legs, duplicate directions, mismatched accounts, altered amounts, corrected legs and orphan references are reported as **NEEDS_REVIEW** instead of being silently considered balanced. Duplicate source IDs and invalid imported identities are rejected entirely because their history cannot be attributed reliably. Deleted transfer headers are excluded from active transfer history but their still-present Bank Book legs are reported as orphan audit evidence. The proof leaves all data unchanged, adds no public route, and cannot replace M03's production posting/auth/replay integration.

## Design, ownership and dependencies

- **M08-only paths:** `tests/fixtures/m08-d1-transfer-header-schema.mjs`, `tests/fixtures/m08-d1-transfer-provenance-preview.mjs`, `tests/integration/m08-d1-positional-cash-workerd.spec.mjs`, this M08 spec and matching plan. Reuse existing `M08_BANK_DDL` with a new test-only `M08_TRANSFER_DDL` table for BANK_TRANSFERS headers. Do not touch shared `src/db`, `migrations`, `src/rpc`, Worker entry, global CI or frozen GAS.
- **API:** `auditD1BankTransfers(DB,{tenantId})` returns `{transfers:[{transferId,fromAccountId,toAccountId,amount,status,reasons,outEntryId,inEntryId}],orphanLegs:[{entryId,reference,type}],summary:{balanced,needsReview,orphanLegs}}`. All transfers are sorted by source header `legacy_row`, orphans by Book `legacy_row`. Amounts come from integer cents, not unverified floating-point import strings.
- **Error and integrity rules:** duplicates in any tenant's original account ID, transfer ID or Bank Book Entry ID are fatal; blank/malformed source IDs or bad ISO calendar dates are fatal. Missing referenced account, same-account transfer, zero/negative header amount, missing/duplicated legs, reference/account/amount mismatch, reversed or manually corrected leg each generate a deterministic `NEEDS_REVIEW` reason. Non-transfer Bank Book entries cannot satisfy a transfer and a missing/deleted header cannot silently absorb an orphan transfer leg.
- **Source fidelity:** transfer header fields and the two legs are obtained from original source GAS in tests using synthetic stubs. Historical inactive bank accounts are allowed in audit (accounts may have been deactivated since posting); this is a reconstruction check, not a new authorization to transfer to inactive accounts. Manual `reverseBankEntry` creates a separate mirror row and preserves the original with `Status='Reversed'`; this audit flags the original transfer for review rather than declaring the reversal complete without both paired transfer corrections.
- **Security/readiness:** tenant comes solely from the strict test request, not a caller-supplied auth context. No real D1, no live tenants, no bank/cash writes, no public financial RPC and no automatic role settlement. The **transactional integration gate remains BLOCKED** pending M02 source identity reconciliation, M03 single posting kernel, M04 SQL-time authorization and M06 source cash-session/payment contracts.
