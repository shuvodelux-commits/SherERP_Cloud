## Original source contract and decision

The frozen FinanceModule defines nine transaction types. Each maps to **exactly one** separate account: `owner` (equity/drawings), `loanPayable` (lender debt/credit), or `borrowerReceivable` (borrower receivable/credit). Signed movements use `amount * balanceEffect`; a positive/negative position is split into six **gross**, not net, totals. `Opening Owner Capital`, `Opening Loan` and `Opening Borrower Loan` are historical positions with `cashDirection:'none'`, not live drawer movement. Different accounts of the same verified person must never cancel one another.

Considered approaches: (1) enable live finance RPC/D1 writes now—rejected due to posting/authorization gates; (2) a combined person Current Due or name-based alias resolver—rejected under ADR-007; (3) **chosen:** one pure module taking preloaded active finance transaction rows with authoritative original `Person ID` already present. It returns per-person **separate** signed account balances plus the legacy six gross summary totals. No SQL, permissions, sessions, UI, or cash/bank calls. Execute pinned source `financeSignedBalances_` and `financeBalanceSummary_` in test-only VM as the parity oracle for eligible ID-bearing rows.

## Minimal interface / semantics

`projectFinanceRoleBalances(activeFinanceRows, {personId} = {})` returns `{byPerson,summary}`, where byPerson matches frozen `financeSignedBalances_` keyed by `id:<Person ID>`, with `{personId,person,owner,loanPayable,borrowerReceivable}`. `summary` matches frozen `financeBalanceSummary_`: `ownerCapital,ownerAdvance,outstandingLoan,lenderCredit,borrowerReceivable,borrowerCredit`. `personId` optional, but if provided selects only that exact source ID. The input ordering follows original `activeRows_('FINANCE_TRANSACTIONS')` posting order; increment each account with `roundMoney_` at each row. Do **not** sort, net accounts, or round at end only. `byPerson` never uses name, mobile or Party external ID as identity.

**Fail closed before calculation:** reject non-array/Promise inputs; rows without a nonempty original `Person ID`; unknown Finance transaction types; nonfinite/negative transaction amounts; and soft-deleted rows accidentally passed as active. Legacy name-only transactions require an explicit reviewed identity import/reconciliation queue, not automatic aliasing; this is a deliberate safety restriction relative to the original GAS fallback that groups blank IDs by normalized name. Do not report a partial authoritative balance for such rows. No invented source IDs, no authorization from a Party role, no actual historical opening Cash Book write.
