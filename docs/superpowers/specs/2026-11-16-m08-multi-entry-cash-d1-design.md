# M08 — Multi-entry Cash Reconciliation D1 proof (test-only)

**Owner continuation:** issue #389 after merged PR #370. **Pinned authority:** Mohim_ERP `29aa4a5c7a7062a49e6bf4758beda3a8d62d9ff2`, frozen `legacy/source/CashReconciliation.gs`. No production finance writer or public RPC.

## Module overview (12 sentences)

The original Cash Reconciliation links one or more existing real Cash Book entries to a difference without creating a new business transaction. This slice extends M08's merged single-entry test-only D1 proof to one **closing** difference explained by two or more entries. Source input parsing removes repeated IDs, preserves first-occurrence order, and accepts JSON arrays, CSV and newline forms. Every selected row must exist, be nondeleted, be nonsynthetic, and have the direction required by the cash discrepancy. The rounded signed sum must equal the discrepancy exactly, not simply be within a tolerance. An entry already attributed to a different session or phase is ineligible, even if it is outside the 250-row UI candidate shortlist. A valid new operation must link every selected entry exactly once while retiring the one historical synthetic adjustment. The same D1 transaction must change session expected cash, variance and revision, plus write one immutable receipt and one audit event. A failing second link, adjustment update, session revision check or audit insertion must roll back the entire operation. Idempotent replay of a stable operation ID and identical canonical entry set must have no additional financial effects. Stale or revoked authority, concurrent competing submissions and inconsistent Cash Book evidence must reject inside SQL rather than trusting JS preflight. Because this is still synthetic, opening differences, source positional marker scanning, actual M02 schema and deployed production posting remain separate release blockers.

## Design decisions and tradeoffs

- Reuse the existing `M08_RECON_DDL` and isolated `seedM08Reconciliation` only as synthetic **auth, session and cash entry fixtures**, adding separate `m08_multi_*` receipt/link/audit/usage tables and triggers. That avoids changing merged single-entry proof or live migrations while exercising real Cloudflare local D1.
- `createSyntheticD1MultiCashReconciliationContract(DB).post(raw)` accepts fixture-owned `{tenantId,actorId,tokenHash,operationId,sessionId,legacyEntryId,revision,now,entryIds}`. Apply the pinned GAS parser to JSON/CSV/array inputs, require 2–16 unique normalized safe ID strings; preserve ordered selection for source-facing documentation and compute a canonical **sorted set** for idempotent semantic equality. This deliberate change in stored order within synthetic proof is not permission to reorder the later production legacy JSON field.
- A **single SQL `INSERT ... SELECT ... WHERE ... RETURNING`** checks authenticated current user/role/tenant/token and versions, active session, revision, exact positive closing difference, selected JSON integrity, selected cardinality, entire Cash Book eligibility and signed sum, no cross-session/cross-phase historical allocation, no already linked real entries, one matching nonzero synthetic adjustment, and no prior closing attribution. SQL uses bound parameters only.
- An **`AFTER INSERT` trigger** retires that adjustment, inserts *every* linked cash ID through `json_each`, checks the inserted count, updates the synthetic session with cent-integer arithmetic and guarded revision, and writes the immutable audit row. `RAISE(ABORT)` failures roll back receipt + all effects. The `DB.batch([CLAIM, READ])` readback matches the existing M08 contract and returns COMMITTED, REPLAY, CONFLICT or DECLINED, or NEEDS_REVIEW on uncertain D1 result.
- Deduplicate the **source input** in JS *before* SQL, but SQL still re-checks set size, types and actual cash rows inside the guarded write. Acceptance tests prove late audit rollback, stale/revoked sessions, cross-tenant and cross-phase allocation, replay with permuted raw input, altered selected set, competing operations and wrong sign/total.
- The expected calculation `opening_cents+sum(selected movements)` is strictly a **controlled isolated fixture** with no in-window cash movements. It does **not** prove the frozen source's physical marker boundaries, late closing attribution, opening exclusion, or full source historical session reconstruction; those remain a later M08 gate. The old `m08_test_*` original receipt/link/audit tables are fixture-only and not used by the new multi writer.
- A dedicated PR-only, no-secret Workerd workflow may run this test in isolation to get fast concrete D1 evidence. The standard M03 integration test suite remains untouched; source test coverage in `npm test` and independent Workerd test are mandatory. No production/staging Cloudflare D1 bindings, frontend changes, scripts against original Sheets, Party auto-netting or cash writers.
