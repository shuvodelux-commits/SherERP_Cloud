# M03 — source-shaped catalog row deletion and physical compaction

**Status:** internal synthetic-test-only D1 repository design. Source: immutable `legacy/source/Database.gs#deleteRow_` and `ProductSettings.gs#setProduct{Category,Unit}Status`; schema: `migrations/0001_core_catalog.sql`.

**Goal:** delete a Category or Unit master and **shift every following `legacy_sheet_row` up by one**, preserving 1-based original Google Sheets row numbering, with an atomic transaction and stale-source preimage guards. Do not change Products' plain-text historical label fields.

**Interface:** `createGuardedCatalogDeleteAdapter(env).deleteRow_(sheetKey,rowIndex,{sourceId,name,status}): Promise<void>`. Only `PRODUCT_CATEGORIES` and `PRODUCT_UNITS`. The source deleteRow_ accepts just rowIndex, but ID+name+status preconditions are mandatory hardening because D1 requests may race. Reject invalid identifiers, wrong/stale preimages, noncontiguous/NULL provenance, >1000 rows, absence of a D1 `batch` method. Only caller's already-authorized product master module should eventually use this; no public route until M04.

**Transactional SQL:** Use `D1Database.batch` of three **fixed, parameterized** statements on one connection/transaction. First guarded `DELETE ... RETURNING legacy_sheet_row` checks exact ID/name/status/index and global contiguous provenance (2..N+1). Second moves rows *after* deletion temporarily above 1002 by adding 1002, guarded by SQLite `changes()=1` from the DELETE. Third maps those temporary indexes to `old-1` by subtracting 1003, guarded by `changes()>0`. This two-phase approach avoids SQLite's immediate UNIQUE index conflicts from a naive ordered UPDATE; the temporary positions cannot exist in valid catalogs of ≤1000 rows. If the delete affects 0 rows, later statements are strict no-ops, and the adapter refuses. A failed middle/last statement must cause batch rollback. Never read first in JS and then write based on a stale snapshot.

**Constraints:** Catalog append / updates / read adapters must remain unchanged. No unapproved delete on SETTINGS, Party, finance, invoices or stock. No public RPC, migration, Cloudflare Worker, credential, workflow or source edit. Permanent deletion never clears historical Product data; same names can be recreated.

**Acceptance:** Node SQLite tests for first/middle/last deletion, physical row identity, stale attempts, concurrent identical requests, null/gap/over-cap provenance, no arbitrary tables, injection attempt; actual workerd+D1 with repeated requests, first-row shift and induced mid-batch failure showing **zero partial state**. A failed or uncertain response requires reconciliation by source ID; not a blind retry with altered preimage. Completeness remains blocked on M04 permissions and full M03 repository.
