## Sales Invoice integration update for #690

Original break confirmed on SherERP Cloud `2185d1c8ed1fcfe51966f64e3111e7e4c0ff98dc`. The repair is based on `c002c8390adf1796880373672ca45d3723ebf159`, after product and Dashboard changes merged. The frozen Sales screen asks for the list first, then Bank accounts, and asks for detail separately. The Owner browser dispatcher routes none of the three names. It rejects them before making a network request. The Sales navigation hook marks its first load complete before the request settles. The existing checkout invoice route accepts `findInvoice`; it has no Sales index and its receipt omits Sales Management return/profit fields. [Original list and Bank calls](../legacy/source/sales.html#L208) · [Original detail](../legacy/source/sales.html#L565) · [First-load hook](../legacy/source/sales.html#L808) · [Owner dispatcher](../scripts/build-owner-frontend.mjs#L477)

Before this repair, the initial notice was unconditional. The Owner session payload hard-codes `dataAvailable:false` even after Control placement and Shop identity verification. The pre-change Owner browser required that field to be false. The Product and Purchase bootstrap could then overwrite that notice, making the contents depend on navigation order. The compiled Owner app now sets the shell notice after verifying the session and shows Sales readiness from each actual Sales response. It does not consult the old dashboard flag. [Old notice, bootstrap and dispatcher](https://github.com/shuvodelux-commits/SherERP_Cloud/blob/2185d1c8ed1fcfe51966f64e3111e7e4c0ff98dc/scripts/build-owner-frontend.mjs#L15) · [Owner session](../src/auth/platform-owner-sessions.js#L60)

## What the Shop Owner can reach at this baseline

Routes below are relative to `/api/owner`. The Owner Worker requires its own origin and session cookie. The pilot binds one Shop D1 and validates the Owner’s active placement and Shop identity. Financial commands also need an unexpired Shop write lease. The original module permissions in the detailed matrix are requirements for staff integration. The pilot currently authenticates Owners only. The production candidate enables Google login and dashboard bootstrap and disables operational catalog, write grants, purchases, POS and returns. A read or write in the pilot column therefore requires a separately configured environment. Screen links identify the enclosing named function when present. Open the linked source to see the original browser call or Apps Script implementation. “Direct groups” lists known source sheet keys referenced as literals inside the named function. Helpers and conditional paths can add dependencies. “Direct check” lists literal permission checks in that function. “Trace helper” means delegated or context-dependent authorization/data access and requires inspection before porting.
