## Source and authority contract

The frozen ProductSettings.gs implements \`addProductCategory(token, payload)\` and \`addProductUnit(token, payload)\`; both require source \`products.add\`. The internal M03 RPC transport recognizes exactly these names, and only if a **trusted caller** supplies the \`productMasterBridge\` option to \`handleRpc\`. The current public Worker at \`src/index.js\` never does this; the public \`src/rpc/registry.js\` remains empty and \`/api/rpc\` still answers 501 for these operations. This feature is intentionally absent from Cloudflare deployments, including public Worker previews.

For private local tests, the payload is strictly \`[token, {name, operationId}]\`. \`operationId\` is a stable idempotency key required by the private D1 writer and **is an internal addition to the original source payload**, so legacy source UI compatibility is not approved. Only a 64-character lowercase-hex bearer, bounded name and canonical operation ID are accepted. The handler rejects client \`actorId\`, \`businessId\`, \`role\`, \`permission\`, \`nowMs\`, SQL, additional fields or methods, including \`postSale\`. It never exposes the raw D1/auth exception, pending Promise, credentials, tenant or unexpected output keys.

The M03 \`createM03PrivateProductMasterBridge(env, {businessId, now})\` obtains its **single-business** D1 binding and \`businessId\` from trusted server construction and calls \`now()\` immediately before each mutation. The bridge never copies clock or business scope from incoming JSON. It delegates to the existing M04 SQL-authorized \`createM04AuthorizedProductMasterCreator\` rather than constructing a second writer. M04's single SQL \`INSERT ... SELECT\` verifies the current nonrevoked bearer digest, session lifetime/idle time, active credential/user and role versions, and literal \`products.add=true\` in the same statement as the trigger-atomic original ID, product row, immutable actor receipt and counter. A preflight or UI display role never authorizes a later mutation.

The original \`{success:boolean,data|message}\` envelope is allowlisted at the transport boundary. Successful IDs must have the correct \`PCAT-\` or \`PUNT-\` six-digit-or-longer canonical prefix, a safe integer suffix and a trimmed name matching the submitted name. The only false envelopes permitted are the two source-required-name/duplicate-name messages for each method. Unauthorized, unexpected or malformed private results fail closed with a generic unavailable response. The original blank-name error stays 200 with a safe \`success:false\` envelope, without any ID allocation.
